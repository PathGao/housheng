反向验证：临时把动作期限从500ms放宽至5000ms，延迟分类结果在573ms触发翻页，真机测试因不该发生的动作失败。恢复500ms后，15项设备测试全部通过。截图存储曾以3项失败复现直接写入的缺口，修复为编码成功后原子替换，4项存储测试通过。内部变量改名不影响纯逻辑测试。

测试启动和退出都会终止被测进程，小米会把无障碍服务留在断开状态。测试准备通过正常设置界面重连用户已授权的后生服务，结束后由验证场进程运行独立恢复步骤，避免再次终止后生。恢复步骤1项通过；13:37系统显示服务已绑定、无崩溃服务，首页确认通知/页面服务都已连接、两项执行均为观察。测试通知和应用内截图已清理。

## 安装和授权

打开开发者选项中的USB调试，接受当前电脑授权。小米设备还可能要求打开USB安装。保持手机解锁，确认来自本次安装的系统弹窗。

安装主应用和验证场APK，打开后生。首页和通知清理页提供通知使用权入口，日常通知功能不要求无障碍。验证场测试的无障碍入口在“设置与诊断”，只勾选“后生验证场”进行首次测试。不会自动更改已有应用通知权限。

设备自动测试在这些授权就绪后运行：

```sh
scripts/test-device.sh
```

脚本安装主应用、验证场及各自测试组件，共四个调试APK。首次需通过验证场正常弹窗允许通知，并在后生入口授予两项特殊访问权限。保持解锁，脚本会重连已授权的后生服务，测试后由验证场测试组件恢复观察状态，不改其他服务。重连先用 shell 写系统安全设置，不读设置页文字。小米未开“USB调试（安全设置）”时拒绝这一步，退回点击中文 MIUI 设置页；其他品牌若也拒绝，需调整测试辅助代码。

服务恢复可单独运行（测试组件已安装时）：

```sh
adb shell am instrument -w io.github.pathgao.housheng.fixture.test/androidx.test.runner.AndroidJUnitRunner
```

## 手动检查

1. **观察默认值**：首次安装默认观察，升级保留通知执行选择。测试时先到“设置与诊断”停止执行。勾选验证场的通知、页面，打开验证场普通信息流，第1条应留在屏幕上。发送4条测试通知，均应保留。
2. **通知清理**：回到后生开启通知执行，再发送4条。营销测试通知应移除，普通通知、消息和常驻通知保留。返回后生刷新记录，应有处理结果和耗时，不含通知正文。
3. **普通内容翻页**：开启内容执行，打开普通信息流，第1条匹配“震惊内幕”后应翻到第2条，并停留。此场景验证系统动作，不验证AI判断。
4. **广告与未知保护**：保持执行开启，分别打开广告保护、未知类型场景。即使命中同一关键词，也应停留在第1条。
5. **截图与停用**：预约5秒后截图，打开已选验证场，再返回后生预览、删除。再次预约后立刻停止所有自动执行，不应生成新截图。
6. **名单与隐私**：真实应用页面选项应显示待适配且不可勾选。浏览器、微信、QQ不出现在内容名单中。它们即使被旧配置选中也必须被运行时过滤，不能读取页面/通知或截图。
7. **安装清单**：打开应用清单页时不应立即查询。主动刷新后应显示当前可见启动器应用，按系统首次安装时间标记近30天。复制/分享必须先预览；关闭/清空后不保留持久化清单。点选应用只打开系统详情，不自动卸载。
8. **统计**：验证场普通信息流产生未分类展示计数，广告与未知页不计入。真实应用没有样本时显示无有效样本，验证数据不能混入真实统计。清空记录后计数归零。

完成后点击“停止所有自动执行”，清除测试通知与截图。无需测试时，可在系统设置撤销后生的两项特殊访问权限。

## 指标口径

翻页耗时从服务收到事件开始，到发出系统滚动动作前计时，包含本地读取、关键词判断和执行前再核对。不含应用首次绘制到系统派发事件的延迟，不代表云模型延迟。500ms是拒绝过期动作的门限，不是尚未实测的性能承诺。

截图耗时从调用系统截图接口到图片写入缓存，不含5秒预约等待。通知耗时是收到回调至发出移除请求，移除是否完成由系统实际通知列表验证。

## 正常使用与重复授权排查（2026-10-03 13:44）

用户担心使用几次就要重授权。检查小米10S保留的最近16条后生退出记录，全部为测试开始/结束引起的FORCE STOP，最近一次为13:34:17 finished inst。此前测试辅助代码主动关闭再开启已授权服务，因此出现小米风险确认。该流程只在测试组件中，主APK没有自动撤销或反复申请无障碍的逻辑。

未运行instrumentation的对照：10轮“验证场→桌面→后生”，每轮检查服务绑定、已启用列表与PID。10轮均保持授权/绑定，PID始终20593。随后退到桌面106秒，再查服务仍绑定、无崩溃服务、同一PID。检查结束未锁屏，不能据此声称锁屏或长时间后台已通过。原始记录在 `.tools/normal-lifecycle-check.json`、`.tools/normal-lifecycle-exit-info.txt`。

短测仅说明常规切换未复现，不能证明自然内存回收、清理最近任务、重启、断开USB后的省电和24–72小时稳定性。无障碍长期可靠性仍是实用化准入条件，前轮15项测试只是功能链路通过。

代码发现：MainActivity在FeedService.instance为空时统一提示“请先开启无障碍服务”，没有区分未授权与已授权但断连，会误导用户重复授权。另外自动执行选择仅在内存中，进程重新建立会回到观察，即使权限仍在也不会自动继续筛选。这两项是当前基础验证版的局限。本轮只诊断，没有修改产品逻辑或系统设置。

建议下一阶段优先验证服务生命周期，至少覆盖24–72小时日常使用、自然回收、锁屏、省电和重启。如果日常操作持续要求重新授权，不应将跨应用自动筛选作为父母版必须依赖的主流程。建议区分授权/连接/执行状态，并在可靠性验证后决定是否持久化用户的执行选择。
